# Contract: Cross-Repo Boundary

## Purpose

Define the authoritative boundary between `archive-graph-data` and
`archive-graph-spacy` for canonical records, derived enrichment, candidate
assertions, reviewed assertions, and promoted overrides.

This contract describes guarantees and handoff rules for dependent roadmap
work. It is not an implementation-specific schema or API design.

## Reference Model

- This contract is published in `archive-graph-spacy` as the authoritative
  boundary definition.
- `archive-graph-data` and `archive-graph-spacy` should reference this contract
  and the linked ADR rather than restating ownership or join semantics in
  separate local planning documents.
- Changes to the boundary should update this contract and
  `docs/adr/002-cross-repo-contract.md` together.

## Source Inputs

- Canonical records owned by `archive-graph-data`
- Effective canonical identifiers issued by `archive-graph-data`
- Derived evidence and candidate assertions generated by `archive-graph-spacy`
- Review decisions, curation state, and promoted overrides maintained by
  `archive-graph-data`

## Owned Surfaces

### Canonical Records

- **Owner**: `archive-graph-data`
- **Examples**: Canonical people, interactions, durable overrides
- **Required guarantees**:
  - Canonical records are the source of truth
  - Cross-repo references use immutable canonical IDs
  - Canonical state is not mutated by derived workflows directly

### Derived Enrichment

- **Owner**: `archive-graph-spacy`
- **Examples**: Search enrichment, NLP evidence, explanation surfaces,
  candidate-supporting evidence
- **Required guarantees**:
  - Derived outputs remain non-canonical and replaceable
  - Every output includes provenance back to canonical inputs or source
    evidence
  - Confidence semantics are documented consistently

### Candidate Assertions

- **Owner**: `archive-graph-spacy`
- **Examples**: Relay-sender identity candidates, disambiguation candidates,
  future evidence-backed proposals before review
- **Required guarantees**:
  - Candidate assertions are pre-review only
  - Every candidate assertion includes assertion type, evidence references, and
    confidence
  - Candidate assertions do not change canonical state

### Reviewed Assertions

- **Owner**: `archive-graph-data`
- **Examples**: Accepted, rejected, superseded, and queued review records
- **Required guarantees**:
  - Human review begins only after candidate handoff into
    `archive-graph-data`
  - Review history is durable and auditable in one curation system
  - Reviewed assertions preserve evidence lineage from the originating
    candidate

### Promoted Overrides

- **Owner**: `archive-graph-data`
- **Examples**: Durable canonical corrections or overrides produced after
  accepted review
- **Required guarantees**:
  - Promotion occurs only from eligible reviewed assertions
  - Promotion rules are explicit by assertion type
  - Promoted facts remain traceable to the reviewed assertion that created them

## Join Key Rules

- Immutable canonical IDs are the only authoritative cross-repo join keys.
- Names, emails, aliases, handles, and other natural identifiers may be stored
  as evidence or lookup aids, but they are not authoritative join keys.
- Any new shared surface added by downstream roadmap work must declare the
  canonical IDs it uses for joining before implementation begins.

## Provenance And Confidence Rules

- Derived enrichment, candidate assertions, and reviewed assertions must all
  preserve source evidence references.
- Confidence meaning must be documented consistently across derived and review
  workflows so downstream users can interpret weak and strong evidence
  uniformly.
- Promotion eligibility must consider both review state and provenance minimums,
  not confidence alone.

## Review And Promotion Rules

- Assertion types must be classified as one of:
  - `derived_only`
  - `reviewable`
  - `promotion_eligible`
- Candidate assertions move from `archive-graph-spacy` to `archive-graph-data`
  before any human review activity occurs.
- Reviewed assertions may end in `accepted`, `rejected`, `superseded`, or
  `promoted` outcomes, but only promotion-eligible types may create durable
  canonical overrides.
- Accepted-but-not-promoted reviewed assertions remain part of durable review
  history and must not be collapsed into canonical override storage.

## Scope Rules

- This v1 contract covers only the roadmap surfaces currently blocked by the
  cross-repo boundary question.
- The contract is intentionally technology-agnostic and does not prescribe API,
  table, or queue implementations.
- Downstream features may extend the contract, but they may not contradict the
  ownership, join-key, provenance, or review-boundary guarantees defined here.

## Deferred Questions

- Which first-wave assertion types beyond relay-sender identity and
  disambiguation should become `promotion_eligible`?
- What minimum review metadata should be required before a reviewed assertion
  can move from `accepted` to `promoted`?
- What lightweight validation step should downstream repos use to confirm they
  still point to this shared contract after future refactors?
